## 2. Facts that bound the target (sources in the research notes, docs.polymarket.com)
- Origin is AWS eu-west-2 behind Cloudflare; no region hostname, no bypass. From London: edge RTT ~1-2 ms, origin in-region.
- BTC 5m market: `seconds_delay: 0` (GET /markets/<cid>, checked 11:3x) - no 50 ms taker hold. `minimum_tick_size 0.001`, min size 5.
- Every order is EIP-712 signed by the wallet key (unavoidable). coincurve is in the venv: sign ~0.2-0.5 ms; our 9.8 ms is thread hop + draft + hash.
- One POST /order per attempt already (SDK `post_order`, httpx HTTP/2, pooled, keepalive 30 s). Pool kept warm only by accident (venue_truth_loop every 20 s).
- Rate limits are not a constraint at our volume. Batch /orders has worse tail latency; not useful for a single order.
- No public measurement of origin processing time exists. The 100 ms target is decidable only by measuring from London.

## 4. Slippage (owner: "maybe add slippage") - a dial, not a gate
Tick on this market is 0.001, so today's `--pad-ticks 1` = cap ask+0.001: any move rejects the FAK. A FAK at cap pays the
book, not the cap, so a wider cap costs nothing when the book has not moved and buys the fill when it has.
Grid on London LIVE by alternating candles, whole grid, both arms: cap pad {0.001, 0.005, 0.01, 0.02}. Report fill rate on
attempt 1, paid - signal quote, per $1 graded on venues.outcome, n per cell (>=60 before reading).
EV eligibility stays judged at ask+1 tick (poly_core.py:318) - the pad changes what we pay, never whether we fire.
